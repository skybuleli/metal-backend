📦 利用现有着色器缓存作为测试数据
关键发现：Ryujinx 的磁盘缓存可以直接作为测试数据集。

Ryujinx 着色器缓存位置：
%appdata%/Ryujinx/games/[GameID]/cache/shader/

缓存文件格式（已从源码确认）：
• guest.toc + guest.data — 原始 Maxwell 着色器代码
  格式：TOCG magic, 包含每个着色器的偏移+大小+CB数据大小+哈希
• shared.toc + shared.data — 翻译后的 Host 着色器
  格式：TOCS magic, 包含 CodeGenVersion 和编译产物
• BinarySerializer 类处理序列化/反序列化

利用方式：
1. 提取 guest.data 中的原始 Maxwell 二进制
2. 喂入我们的着色器翻译管线
3. 对比输出（与已知 Good-Known 结果对比）
4. 使用 shared.data 中已有的 GLSL/SPIR-V 作为参考

第二部分：调试与反汇编工具链

从 Maxwell SASS 反汇编到 Metal GPU 帧捕获的完整调试生态

🔧 Maxwell 端：理解着色器输入
envydis✅ 核心工具NVIDIA Maxwell SASS 反汇编器。用法：envydis -V gm107 shader.bin。生成人类可读的 Maxwell 汇编代码。
nvdisasm🟡 辅助NVIDIA 官方反汇编器（CUDA 工具包自带）。覆盖更多架构。
UAM (nv50_ir)✅ 核心Mesa/nouveau 的 Maxwell 代码生成器。nv50_ir_print.cpp 可打印 IR → 理解优化过程。
nvcachetools🟡 辅助提取 NVIDIA GLCache 中的编译着色器进行分析。
🔄 中间层：验证着色器翻译
spirv-val✅ 核心SPIR-V 模块规范验证器。验证生成的 SPIR-V 合法性。
spirv-dis🟡 辅助SPIR-V 二进制反汇编器。
spirv-cross🟡 辅助SPIR-V → GLSL/MSL/HLSL 转换。用于交叉验证 Slang 输出。
glslangValidator✅ 核心GLSL→SPIR-V 编译器。验证 Ryujinx GLSL 输出的合法性。
slangc --debug🟡 辅助Slang 编译器的调试输出模式。
🍎 Metal 端：验证渲染输出
Xcode Metal Debugger✅ 核心GPU 帧捕获、逐行着色器调试、资源检查。启用：Scheme → GPU Frame Capture。
MTL_SHADER_VALIDATION✅ 核心Metal 着色器运行时验证。环境变量 MTL_SHADER_VALIDATION=1。
MTL_DEBUG_LAYER✅ 核心Metal API 调用验证。环境变量 MTL_DEBUG_LAYER=1。
MTL_CAPTURE_ENABLED🟡 辅助Metal 帧捕获开关。dxmt 已集成此功能。
Instruments GPU Trace🟡 辅助CPU+GPU 时间线、内存使用、性能计数器。
🔗 端到端：全链路调试
dxmt capture🟡 辅助DXMT_CAPTURE_EXECUTABLE + F10 热键生成 Metal 帧捕获。
Apitrace⚪ 可选OpenGL 调用追踪（对比参考）。
GPU 像素差异分析✅ 核心自建工具：渲染同一帧到离屏纹理 → 像素级对比 → 差异热力图。
注意：RenderDoc 不原生支持 Metal。苹果生态下的 GPU 调试必须使用 Xcode Metal Debugger。

第三部分：集成方式 — 如何介入现有模拟器

分支策略、验证路径和最小可行集成的选择

策略 A：独立库 + 适配层
推荐
做法：
• Metal 后端作为独立 C/C++ 动态库开发
• 通过 C API 暴露给上层
• 编写适配层对接 Ryujinx/Astris 的 GAL 接口
优势：
• 可在任何模拟器中使用
• 独立测试和调试（不依赖模拟器启动）
• 清晰的模块边界
劣势：
• 需要多一层适配代码
策略 B：Astris fork 分支
适用 Phase 2+
做法：
• Fork Astris（macOS 原生分支）
• 在其 GPU 后端框架中新增 MetalBackend
• 实现 GAL IRenderer 接口
优势：
• 直接运行游戏验证
• 复用 Astris 的 UI/音频/输入
劣势：
• 依赖 Astris 上游更新
• C# 与 Metal (ObjC/C++) 互操作复杂
策略 C：独立验证工具
Phase 1 推荐
做法：
• 构建独立的着色器编译+渲染测试工具
• 输入：Maxwell 着色器缓存文件
• 输出：渲染结果 + 性能指标 + 差异报告
优势：
• 最快启动（无需模拟器集成）
• 专注验证着色器翻译核心
• 可作为 CI 自动化测试
劣势：
• 仅验证着色器，不验证 NVN 命令翻译
🎯 推荐路径：渐进式集成（三阶段）
Phase 1：策略 C — 独立验证工具
开发 shader-validator 命令行工具。
• 读取 Ryujinx 缓存 → 解码 Maxwell → Slang 编译 → Metal 渲染 → 离屏像素对比
• 不需要运行任何模拟器，纯着色器翻译验证
• 可作为 CI pipeline 中的自动化测试步骤
Phase 2：策略 A — 独立 Metal 后端库
将验证过的着色器编译器和命令翻译逻辑打包为 libswitch-metal.dylib。
• C API 设计，与 GL/Vulkan/Metal 后端接口对齐
• 可从独立测试程序调用，验证完整渲染管线
Phase 3：策略 B — Astris/Ryujinx fork
将 Metal 后端库集成到 Astris（或 Ryujinx 镜像）中。
• 实现 IRenderer 接口 → 对接 GAL
• 完整的游戏运行验证

第四部分：CI/CD 与自动化测试

🤖 自动化流水线
每个 PR / Commit 触发：
• 编译检查（ARM64 + x86_64）
• 单元测试（GTest/Catch2）
• Slang GLSL→MSL 冒烟测试（≥10 个基础着色器）
• Metal 验证层检查（MTL_SHADER_VALIDATION=1）

每日 Nightly：
• 全量着色器缓存回归测试
• 像素级 GPU 渲染对比（与 MoltenVK 路径）
• 性能基准采集和趋势图

发布前：
• ≥5 款游戏完整帧渲染测试
• 内存泄漏检测（ASan/LSan）
• 着色器覆盖率报告 ≥95%
📊 测试基础设施
测试框架：
• C++: GoogleTest (GTest) + Google Mock
• Metal: 自建 Metal 测试 Harness
• 着色器: 自定义 pytest 脚本

测试数据管理：
• 从公开着色器缓存库（Ryujinx 社区共享）提取
• 按游戏/着色器类型分类存储
• Git LFS 管理大型二进制测试文件

结果可视化：

总结

✅ 测试策略
1. 测试金字塔：单元（指令级）→ 集成（着色器管线）→ 回归（游戏帧对比）
2. 充分利用现有缓存：Ryujinx 的 guest.data 可直接提取为测试数据，shared.data 提供 GLSL/SPIR-V 参考
3. 每个 Phase 有明确退出标准：量化指标（编译成功率、像素差异率、Metal 验证零错误）
🔍 调试工具
1. 全链路覆盖：Maxwell(envydis) → IR(spirv-val) → GLSL(glslangValidator) → MSL(Slang debug) → Metal(Xcode Debugger)
2. Metal 专属：Xcode GPU Frame Capture + MTL_SHADER_VALIDATION + MTL_DEBUG_LAYER 三重保障
3. RenderDoc 不可用：Metal 生态下必须使用 Apple 原生工具
🔗 集成方式
1. 渐进式：独立工具(Node) → 独立库(Lib) → 模拟器集成(Fork)
2. Phase 1 不碰模拟器：用独立 shader-validator 工具验证核心着色器翻译
3. Phase 2-3 再集成：先做 libswitch-metal.dylib，再通过 P/Invoke 对接 Astris 的 C# 层
