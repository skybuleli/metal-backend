🔄 Agent Operations Manual
Checkpoint 系统 & 工作流设计

本文档描述如何让 Agent Coder 在多次会话间保持连续性。配合 Blueprint 使用。

1. 设计理念：为什么要自己设计，不依赖框架

核心洞察：Superpowers、GSD、AutoGPT 等 Agent 框架解决的是"如何调用工具"的问题。但真正的痛点不是工具调用，而是 Agent 在每次新会话中不知道做到哪了。这个断片问题，任何框架都解决不了——它只能通过一个持久化的状态文件来解决。

我们的方案：文件驱动状态机——一套纯 markdown 文件，Agent 读写它们就像读写代码文件一样自然。不绑定任何特定框架，但任何框架的 Agent 都能用。

2. 核心文件：PROGRESS.md（Checkpoint 状态机）

这是整个系统的心脏。每次 Agent 完成任务后必须更新这个文件。下次 Agent 启动时首先读取它。

📄 PROGRESS.md
项目根目录。Agent 每次会话的第一条指令就是读取此文件。

2.2 Agent 读取 PROGRESS.md 后的行为

Session Resume Protocol
① 找到第一个 🔄 in_progress → 继续该任务
② 如果没有 in_progress，找第一个 ⬜ pending → 开始该任务
③ 更新该任务状态为 🔄，记录开始时间
④ 执行任务
⑤ 完成后更新状态为 ✅，记录完成时间和证据文件
⑥ 如果有 🚫 blocked，评估是否需要报告用户
⑦ Commit: feat(scope): P{X}.{Y} task description [done]

4. 文件体系总览

文件类型谁写谁读更新频率

5. Agent 会话完整生命周期

🔁 每次会话的标准流程
STEP 0 — 启动
Agent读取 NEXT_TASK.md（如不存在则读取 PROGRESS.md 并自行判断）

STEP 1 — 认领
在 PROGRESS.md 中标记当前任务为 🔄 in_progress，写开始时间

STEP 2 — 执行
按照 NEXT_TASK.md 中的步骤执行。遇到阻塞立即标记 🚫 并记录到 Blockers 表

STEP 3 — 验证
检查出口准则是否全部满足。记录证据（log文件、截图、测试输出）

STEP 4 — 完成
标记任务为 ✅ done，写完成时间和证据路径。更新完成度百分比。更新 Phase 状态

STEP 5 — 持久化
① commit PROGRESS.md ② commit 代码变更（Conventional Commits格式）③ 运行 python tools/gen_next_task.py ④ commit NEXT_TASK.md（如有变更）

STEP 6 — 追加会话日志
在 SESSION_LOG.md 追加本次简短记录：时间、任务、结果、遇到什么问题

7. gen_next_task.py — 自动生成器

#!/usr/bin/env python3
"""从 PROGRESS.md 自动生成 NEXT_TASK.md"""
import re, datetime

def parse_progress(path="PROGRESS.md"):
    with open(path) as f:
        content = f.read()
    
    # 找第一个 in_progress 任务
    in_progress = re.findall(r'\|\s*(P\d+\.\d+)\s*\|(.+?)\|\s*🔄', content)
    if in_progress:
        return {"task_id": in_progress[0][0], "desc": in_progress[0][1].strip()}
    
    # 找第一个 pending 任务
    pending = re.findall(r'\|\s*(P\d+\.\d+)\s*\|(.+?)\|\s*⬜', content)
    if pending:
        return {"task_id": pending[0][0], "desc": pending[0][1].strip()}
    
    return None

def gen(task):
    now = datetime.datetime.now().isoformat()
    return f"""# NEXT TASK — {now}
# 自动生成: tools/gen_next_task.py

## 📍 当前位置
- 当前任务: **{task['task_id']}** — {task['desc']}

## 🎯 你的任务: {task['task_id']}
请查看 Blueprint §6 中对应的任务描述和 Agent 执行提示。

## 🚀 完成后的Commit消息
```
feat(scope): {task['task_id']} {task['desc'].lower()} [done]
```
"""

if __name__ == "__main__":
    task = parse_progress()
    if task:
        with open("NEXT_TASK.md", "w") as f:
            f.write(gen(task))
        print(f"Generated NEXT_TASK.md → {task['task_id']}")
    else:
        print("🎉 All tasks complete!")

8. 关于 Agent 框架（Superpowers / GSD 等）

我们的立场：文件驱动 > 框架绑定

这套 Checkpoint 系统是框架无关的。无论 Agent 运行在 Ally Coder、Claude Code、Cursor、Windsurf、还是任何其他平台上，只要它能读写文件，就能用。

如果未来想引入 Superpowers 或 GSD 的工作流编排能力，它们可以在这套文件之上运行——读取 NEXT_TASK.md 获取当前任务，执行完成后更新 PROGRESS.md，形成闭环。但核心的状态管理始终在文件中，不绑定到任何框架的数据库或内部状态。

原因：框架会变、会停更、会被替换。但一套结构化的 Markdown 文件，10年后还能用。

9. 渐进式复杂度：从简单到自动化

阶段复杂度操作方式适合时机
Level 1最低Agent 手动读写 PROGRESS.md，Human 手写 NEXT_TASK.md项目初期（P0-P2），任务少
Level 2低Agent 手动更新 PROGRESS.md，gen_next_task.py 自动生成 NEXT_TASK.mdP3-P5，任务增多
Level 3中Agent 调用 gen_next_task.py；Git pre-commit hook 自动验证 PROGRESS 格式P6+，需要严格管理
Level 4高CI bot 自动监控 PROGRESS.md 变更 → 自动更新 GitHub Project board → 自动分配 Issue多人协作 + 发布后

🔚 总结：如何让项目顺畅运行

① Blueprint = 宪法，记录"该做什么"
② PROGRESS.md = 仪表盘，记录"做到哪了"——每次任务完成后更新
③ NEXT_TASK.md = 导航仪，告诉下一个 Agent "你现在做什么"
④ SESSION_LOG.md = 黑匣子，记录"发生了什么"
⑤ Conventional Commits = 轨迹，每次完成一个任务就 commit 一个
⑥ gen_next_task.py = 自动挡，从 P3 开始自动化

这四个文件 + 一个脚本 + 提交规范 = Agent 永不断片。不管换了多少个 Agent 会话，每个新 Agent 打开 NEXT_TASK.md 就知道自己该干啥。
