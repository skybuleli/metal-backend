零、新增方案：deko3d/UAM + Slang 联合技术栈

本版报告新增的核心分析内容

🔑 关键洞察
deko3d + Slang 的组合从根本上改变了着色器翻译的技术路线选择。
deko3d/UAM 提供了 Maxwell GPU 的完整知识体系（寄存器定义 + GLSL→Maxwell 编译器）， 而 Slang 提供了从类 HLSL/GLSL 到 Metal MSL 的直接编译能力。 两者的结合使得从 Maxwell 着色器到 Metal 的转换可以绕开 DXBC 中间格式和 MoltenVK 翻译层， 形成一条近乎直接的路径。
📦 deko3d + UAM
devkitPro · C++ · 394 stars · Maxwell 硬件级知识
deko3d 是 Switch 自制软件的低级 3D 图形 API，本质上是 NVN 的开源替代品。

核心资产：
• engine_3d.def — 完整的 Maxwell 3D Engine 寄存器定义（200+ 寄存器）
• gpu_3d_state.cpp — GPU 3D 状态机实现
• image_formats.cpp — 像素格式映射表
• dk_shader.h/cpp — DKSH 着色器二进制格式

UAM（devkitPro/uam, 25 stars）是基于 Mesa GLSL 解析器 + Nouveau nv50_ir 后端的 Maxwell 着色器编译器：
• 输入：GLSL（兼容 Mesa 19.0.8 特性）
• 输出：原生 Maxwell SASS 机器码（.dksh）
• 支持 Maxwell 双发射调度优化
• Maxwell GM107 指令编码（emit_gm107.cpp）
🔧 Slang 着色器语言
NVIDIA 主导 · C++ · 5,364 stars · 多目标编译器
Slang 是 NVIDIA 主导的开源着色器语言和编译器，支持"一次编写，到处运行"。

支持的输出目标：
• D3D11 (HLSL) · D3D12 (DXIL) · Vulkan (SPIR-V)
• Metal (MSL) — 实验性但功能完整
• CUDA (C++) · CPU (C++) · WebGPU (WGSL)

Metal 后端能力：
• 生成人类可读的 MSL 代码
• vertex/fragment/compute/mesh 着色器
• 完整的系统语义映射（SV_* → Metal [[attribute]]）
• 资源类型映射（ConstantBuffer→constant*, Texture2D→texture2d）
• IR 合法化 pass 专门针对 Metal 调整

二、为什么 deko3d + Slang 改变了游戏规则

技术路线选择逻辑的范式转变

🔬 deko3d：从"逆向 NVN"到"理解 Maxwell"

deko3d 的价值远超一个简单的自制软件 API。它是 fincs 一年半逆向工程 NVN 的结晶，提供了 Maxwell GPU 硬件层的完整知识映射。

对我们的直接价值：
 • engine_3d.def 中的每个寄存器定义都对应一个 NVN 函数调用 → 我们可以建立 NVN→Metal 的直接映射表
 • gpu_3d_state.cpp 展示了 Maxwell 3D 管线状态如何管理 → 可直接映射到 Metal 的 RenderPipelineDescriptor
 • UAM 的 nv50_ir 编译器展示了 Maxwell 指令如何编码 → 反汇编/验证参考
 • DKSH 格式公开了着色器二进制布局 → 验证我们的解码器正确性

实际案例：deko3d 的 RenderTarget 寄存器定义告诉我们：每个 RT 有 Addr、Format、TileMode、ArrayMode 等属性。这些直接对应 Metal 的 MTLRenderPassDescriptor 配置。NVN→Metal 的命令映射不再需要猜测。
⚡ Slang：从"造编译器"到"用编译器"

Slang 是 NVIDIA 研究院 5+ 年持续投入的着色器编译器项目，支持 10 个目标平台。它的 Metal 后端虽然标记为"实验性"，但实际功能相当完整。

对我们的直接价值：
 • Slang 接受 GLSL 输入 → 我们不需要写自己的着色器编译器
 • Metal MSL 代码生成经过了系统语义映射、IR 合法化、类型展平等多个 pass
 • Slang 的模块系统允许我们复用已有 Shader 库
 • NVIDIA 持续维护 → 新 Metal 特性会被跟进

关键对比：写一个 Maxwell→DXBC 编译器需 4-6 个月（v1.0 方案的最大风险）。而将 Ryujinx 现有的 Maxwell→GLSL 管线（已完成）连接到 Slang 的 GLSL 输入，只需验证和适配，约 1-2 个月。

四、关键技术决策点

需要验证和权衡的核心问题

⚖️ 决策 1：GLSL vs SPIR-V 作为 Slang 输入
推荐：GLSL 优先，SPIR-V 作为备选

GLSL 路径优势：
• Ryujinx 的 GLSL 代码生成器已非常成熟
• Slang 原生支持 GLSL 语法（通过兼容模块）
• GLSL 文本可直接调试和修改
SPIR-V 路径优势：
• SPIR-V 是二进制格式，无文本解析开销
• Slang 可以通过内联 SPIR-V 支持
• 但会失去 Slang IR 优化的机会

结论 Phase 1 验证两者，优选 GLSL
⚖️ 决策 2：Metal 后端：dxmt 复用 vs 自研
推荐：混合方案

复用 dxmt 的部分：
• dxmt_device：MTLDevice 创建和管理
• dxmt_command_queue：命令队列和提交
• dxmt_buffer/texture：资源分配和生命周期
• dxmt_presenter：MetalLayer 呈现 + MetalFX
自研的部分：
• NVN→Metal 命令编码器（核心差异化逻辑）
• Maxwell 管线状态→Metal PSO 映射
• 着色器资源绑定表管理

结论 dxmt 提供基础设施，命令翻译自研
⚖️ 决策 3：deko3d 作为参考 vs 作为代码
推荐：作为权威参考文档

deko3d 是 C++ 库（目标 Tegra X1），我们的后端是 C++/ObjC（目标 Apple Silicon）。

直接使用的部分：
• engine_3d.def → 生成 Maxwell 寄存器映射表
• image_formats.cpp → 像素格式转换参考
参考理解的部分：
• gpu_3d_state.cpp → 理解 Maxwell 3D 管线状态模型
• UAM 的 nv50_ir → 理解 Maxwell SASS 编码

结论 知识迁移，不直接链接
⚖️ 决策 4：Slang 集成方式
推荐：slangc 命令行 + libslang 动态库

Phase 1: 命令行模式
• 使用 slangc CLI 工具验证 GLSL→MSL 转换
• 快速原型验证，无需代码集成
Phase 2: 库集成模式
• 通过 libslang 动态库内嵌编译器
• 使用 slang.h C API
• 支持运行时着色器编译和缓存

注意 Slang Metal 后端标记为实验性，需监控上游更新

八、结论

✅ v2.0 核心结论

deko3d/UAM 和 Slang 的引入显著提高了项目成功的概率。


deko3d 的核心贡献：将 NVN 命令映射从"猜测"变为"查阅文档"。engine_3d.def 提供了 Maxwell GPU 寄存器的完整定义，使 NVN→Metal 的命令翻译有了精确的参考。


Slang 的核心贡献：消除了"自建着色器编译器"这个最大的技术和时间风险。通过将 Ryujinx 已有的 GLSL 管线接入 Slang 的 Metal 后端，着色器翻译的工作量从 4-6 个月降至 1-2 个月。


成功概率提升：从 v1.0 估算的 60-70% 提升至 80-90%。项目总时间从 11-16 个月降至 7-10.5 个月。核心风险（着色器编译器开发）从"高"降为"中低"。

📋 最终行动建议
1. 立即启动 Phase 1 验证：用 slangc CLI 验证 GLSL→MSL 可行性
2. 与 dxmt 社区保持协作：复用 Metal 后端基础设施
3. 将 deko3d 作为"Maxwell 参考手册"：命令翻译的权威知识源
4. 监控 Slang Metal 后端成熟度：作为备选保留 dxmt/airconv
5. 模块化各层：着色器编译器（Slang）、命令翻译（自研）、Metal 后端（dxmt）相互独立
⚠️ 需要注意
1. Slang 的 Metal 后端仍标记为"实验性"，需在 Phase 1 充分验证
2. UAM 是 GLSL→Maxwell，我们需要的是逆向（Maxwell→GLSL），但 Ryujinx 已解决
3. deko3d 是 Tegra X1 的库，不能直接链接到 macOS 项目
4. Nintendo 法律风险依然存在，仅开发翻译层
5. 着色器缓存策略需针对 Slang 编译产物优化
