# P1.9 编译基准脚本规格

> 读者：准备实现 `bench_compile.sh` 的维护者或 Agent。
>
> 读完后的目标动作：能按统一输入分桶、统一统计口径和统一输出格式实现 P1.9，而不是写出一个只会“跑一堆文件然后打印总耗时”的脚本。

## 目标

P1.9 的目的不是重新验证功能正确性。功能正确性已经由 P1.1~P1.8b 的脚本负责。

P1.9 需要回答的是三个问题：

- 哪一类样本编译最快、最稳定
- 哪一类样本会触发回退或失败
- 后续做缓存和回归时，基准数据是否可横向比较

所以 `bench_compile.sh` 必须建立在“样本先分桶，再统计”的前提上。

## 输入分桶

P1.9 至少要读取三类输入，不能混成一个总表。

| 桶 | 来源 | 目的 | 失败语义 |
|----|------|------|----------|
| `must-pass` | 内嵌控制样本 | 作为主线速度和稳定性基线 | 任一失败都应视为回归 |
| `known-good` | P1.6~P1.8b 当前可通过样本 | 作为真实/近真实样本的编译基准 | 失败视为回归或统计漂移 |
| `known-failure` | P1.8b 当前已知失败样本 | 观察失败耗时、失败阶段和错误类型是否变化 | 失败本身不阻断，但错误类型变化要报告 |

不建议在 P1.9 第一版就把全量 `test_output` 直接塞进去。第一版更适合用一组固定的代表样本，避免基准结果被样本总量和机器瞬时状态淹没。

## 第一版推荐样本量

建议控制在 20~30 个输入以内，保证可重复、可读、可比。

- `must-pass`: 6~8 个
- `known-good`: 10~12 个
- `known-failure`: 4~6 个

第一版的重点不是“覆盖越多越好”，而是“同一批样本能在之后重复跑出可比较的数据”。

## 计时口径

每个样本至少记录三段时间：

- `slang_ms`: `slangc` 编译耗时
- `msc_ms`: `metal-shaderconverter` 耗时
- `total_ms`: 总耗时

如果后续要接入回退路径，还应预留：

- `fallback_ms`: 从 Path A 失败到 Path C 成功的耗时

计时规则：

- 用同一种计时方式记录所有阶段
- 同一条样本在一次运行中只统计一次，不做自动重试
- 编译失败时仍要记录已发生阶段的耗时

## 每条记录必须输出的字段

建议每条样本至少输出以下列：

| 字段 | 含义 |
|------|------|
| `bucket` | `must-pass` / `known-good` / `known-failure` |
| `name` | 稳定样本名 |
| `stage` | `vertex` / `fragment` / `compute` |
| `path` | 实际使用路径，第一版以 `A` 为主 |
| `result` | `pass` / `fail` / `expected-fail` |
| `fail_stage` | `slangc` / `msc` / `fallback` / `none` |
| `error_kind` | 例如 `uninitialized`, `semantic-overlap`, `stage-mismatch`, `none` |
| `src_bytes` | 源文件大小 |
| `dxil_bytes` | DXIL 大小，失败时可为空 |
| `metallib_bytes` | metallib 大小，失败时可为空 |
| `slang_ms` | slangc 耗时 |
| `msc_ms` | MSC 耗时 |
| `total_ms` | 总耗时 |

如果没有这些字段，后续很难判断“变慢了”到底是样本换了、路径变了，还是错误类型变了。

## 汇总输出

脚本最后至少需要四类汇总：

### 1. 总体汇总

- 总样本数
- 成功数
- 失败数
- 预期失败数

### 2. 按桶汇总

- 每个桶的成功率
- 每个桶的平均总耗时
- 每个桶的最大耗时

### 3. 按阶段汇总

- VS / FS / CS 的样本数
- VS / FS / CS 的平均总耗时

### 4. 按错误类型汇总

- `uninitialized`
- `semantic-overlap`
- `stage-mismatch`
- `other`

这个维度很重要，因为它能直接告诉我们后续该先修 `CommandMapper`、语义布局，还是阶段识别。

## 第一版不建议做的事

为了让 P1.9 尽快落地，第一版不建议同时做这些事：

- 不要跑全量 `test_output`
- 不要在第一版就引入复杂并行
- 不要把 Path A / C / B 的所有组合一次性做完
- 不要把 JSON、CSV、Markdown 报告三种格式一起上

第一版先把“固定样本 + 清晰表格 + 稳定计时”做好，已经足够支撑后面 P4/P6。

## 与 P4/P6 的关系

P1.9 不是孤立脚本，它会直接喂给后面两件事：

- P4 缓存设计
  需要知道哪类样本编译最慢、哪类错误最值得短路或回退。

- P6 回归测试
  需要知道哪些样本属于 `must-pass`，哪些属于 `known-failure` 观察项。

如果 P1.9 把所有样本混在一起，P4 得不到缓存优先级，P6 也得不到可持续的回归分桶。

## 推荐的第一版完成标准

P1.9 第一版建议以下标准即可视为合格：

- 固定样本集可重复运行
- 每条样本有结构化输出
- 汇总包含桶、阶段、错误类型三个维度
- `must-pass` 与 `known-good` 不混淆
- `known-failure` 不阻断脚本，但会单独统计

## 结论

`bench_compile.sh` 的价值不在于“多跑几个文件”，而在于把 P1 的编译验证结果转成后续可比较、可缓存、可回归的数据面。

所以 P1.9 的第一优先级是：

- 样本分桶正确
- 统计口径固定
- 输出格式稳定

只要这三件事站稳，后面扩样本、加回退、接缓存都会顺很多。
