# P4 着色器前置风险清单

> 读者：准备进入 P4/P5 的项目维护者或 Agent。
>
> 读完后的目标动作：在实现 `MetalShaderCompiler`、`CreateProgram`、回退逻辑和 `CommandMapper` 时，能判断哪些问题必须先解，哪些可以延后，哪些应明确留给 P8 兼容性阶段。

## 这份清单解决什么问题

P1.6~P1.8b 已经证明 `Path A = Slang → DXIL → MSC → metallib` 的主干能力可用，但真实/近真实语料也暴露出一批稳定失败模式。

当前最大的风险已经不是“工具链能不能跑”，而是“输入给工具链的着色器源码是否足够规范”。如果 P4 把 `MetalShaderCompiler` 做成纯黑盒编译器，而不承担阶段识别、输入规范化、失败分桶和回退决策，后续 P4/P5/P6 会反复在同一类问题上失血。

## 当前已确认的信号

P1.8b 的扩展语料结果：

- `29` 个 Path A 通过
- `0` 个控制样本失败
- `13` 个真实/近真实语料发现问题
- 覆盖 `VS=12 / FS=12 / CS=5`

这些问题目前集中在三类：

- 未初始化临时变量
- varying / semantic 冲突，例如 `TEXCOORD overlap`
- 非 VS/FS/CS 语义混入，例如 `SV_DomainLocation`

这说明 P4 之后的主战场将转向“着色器前端整形”和“失败模式管理”，而不是继续怀疑 MSC 或 slangc 本身。

## 必须先解

这些问题如果不先处理，会直接阻塞 P4 的 `CreateProgram`、P4.2.5 的回退逻辑，或者让 P6 的测试结果不可读。

### 1. 阶段识别与 profile 绑定

必须保证阶段和 profile 一一对应，而不是交给调用方临时拼接。

- Vertex 固定 `sm_6_0`
- Fragment 固定 `ps_6_0`
- Compute 固定 `cs_6_0`

原因：

- P1.7 已证明 fragment 若继续沿用通用 `sm_6_0`，会出现 slangc 返回 0 但不产出 DXIL。
- P1.8 已证明 compute 需要明确走 Slang 原生资源声明，不能混用 GLSL std430 预期。

P4 设计要求：

- `MetalShaderCompiler` 接口必须显式接收阶段枚举，而不是靠文件后缀或源代码片段猜测。
- 编译日志里必须回写“阶段 + profile + 路径”，否则后面无法定位失败模式。

### 2. 输入分类与失败分桶

P4 不能把所有编译失败都当成同一种错误。

至少要分成三桶：

- `must-pass`：控制样本和主线输入，失败就是回归
- `known-good corpus`：当前能通过的真实/近真实样本
- `known-failure corpus`：当前已知会失败，但值得持续跟踪的样本

原因：

- 如果不分桶，P6 回归测试会被“预期失败”和“真实回归”混在一起，日志会再次冗长失真。
- P1.8b 的价值就在于它已经把“主线可用”和“真实语料有坑”拆开了，P4/P6 必须继承这个分层。

P4 设计要求：

- 编译结果对象要带失败类别，而不是只有成功/失败布尔值。
- 失败日志要能写入缓存索引或测试报告，供 P6 使用。

### 3. `CommandMapper` 输出 Slang 原生语法的约束

这个决策已经不是“建议”，而是前提条件。

必须坚持：

- Path A 主线输入使用 Slang 原生语法
- GLSL 保留给 Path C 或交叉验证

原因：

- `std140` / `push_constant` / `std430` 在 Path A 下已经有稳定不兼容记录
- compute 资源声明也已经证明 Slang 原生 `RWStructuredBuffer`、`RWByteAddressBuffer`、`RWTexture2D` 更稳

P4 设计要求：

- `CommandMapper` 的输出契约要面向 Slang 语义，而不是先生成一版“看起来像 GLSL”的中间结果再补丁修复。

### 4. 回退逻辑必须结构化，不是异常兜底

P4.2.5 的回退逻辑不能写成“Path A 抛异常就随便试下一条”。

至少需要：

- 记录当前失败发生在 `slangc`、DXIL 校验还是 MSC
- 判断失败是否值得回退到 Path C
- 把成功路径写入缓存索引，避免每次都重新探测

原因：

- 有些失败是输入语义错误，回退未必能救
- 有些失败明显是 Path A 特有约束，Path C 是合理退路

P4 设计要求：

- 编译返回值需要包含 `失败阶段`、`失败摘要`、`建议回退路径`
- 缓存键不能只存源哈希，最好也存“成功路径”

## 可以延后到 P4 后段或 P5

这些问题重要，但不必卡住 P4 起步。处理方式应该是“先记录、后收敛”。

### 1. 未初始化变量诊断

`real_*`、`kirby_*`、`large_*` 样本里这类问题很多，但它更像是语料质量或前端生成细节问题，不一定要求 P4 第一周就彻底修完。

建议：

- P4 先把它纳入 `known-failure corpus`
- P5 再决定是 `CommandMapper` 做初始化补齐，还是解码端输出约束收紧

### 2. TEXCOORD overlap 与 varying 压缩策略

这已经是明确风险，但它更像“语义布局策略”问题，不是工具链生死线。

建议：

- P4 先让编译器层把这类错误识别并归类
- P5 再结合 `SetVertexAttribs`、资源绑定和 varying 规则统一收敛

### 3. 真实语料的最小化归档

P1.8b 现在记录的是“哪些大样本失败了”，但还没把它们最小化成 P6 的单元/集成样本。

建议：

- P4 期间只要保证错误类型稳定可识别
- P6 再系统抽取最小失败样本

## 明确留到 P8

这些问题在 P4/P5 需要知道它们存在，但不应该为了“现在看起来完整”而提前硬啃。

### 1. `gl_PointSize` / 点精灵兼容

P1 已确认 DXIL SM 6.0 VS 没有 `SV_PointSize` 这条现成语义。这个问题真实存在，但更接近兼容性修复，不该阻塞 P4 主线编译器接通。

### 2. 几何着色器完整兼容

蓝图已经把 GS 放到了 `P5.11`。P1.8b 也进一步说明，非传统 VS/FS/CS 阶段混入时，先做正确分类比现在就强行支持更重要。

### 3. 曲面细分完整兼容

`SV_DomainLocation` 说明 tessellation 风险已经提前显形，但真正的 Maxwell Tess → Metal 解构仍然是后续专题，不适合在 P4 的 `CreateProgram` 阶段一次做完。

## 对实现顺序的影响

建议把 P4 的着色器相关实现拆成四个顺序：

1. 先做“稳定可诊断”的编译器外壳
   目标：阶段明确、profile 明确、日志明确、回退判定明确。

2. 再做“主线输入约束”
   目标：默认只接 Slang 原生主线输入，把 GLSL 输入限制在 Path C 或测试用途。

3. 然后做“缓存索引”
   目标：缓存不仅记二进制，还记成功路径和失败摘要。

4. 最后再做“失败模式收敛”
   目标：把 P1.8b 暴露的真实问题逐步转成 P6 可回归的最小样本。

如果顺序反过来，例如先做缓存、再做日志、最后才补失败分类，会很容易把坏结果长期缓存起来，后面很难读。

## 推荐的 P4 最小能力边界

进入 P4 的最小目标不应该是“真实着色器都能编过”，而应该是：

- Path A 控制样本稳定通过
- `known-good corpus` 可重复通过
- `known-failure corpus` 能稳定归类
- Path A 失败时能按规则判断是否回退 Path C
- 编译缓存知道哪条路径成功过

做到这一步，P4 才算拥有“可开发的着色器地基”。

## 推荐的 P6 测试分桶

为了避免日志再次失控，建议 P6 从一开始就按下面三层组织：

| 桶 | 样本来源 | 判定规则 |
|----|----------|----------|
| `must-pass` | 内嵌控制样本 | 任一失败都阻断提交 |
| `known-good` | P1.6~P1.8b 当前可通过样本 | 失败视为回归 |
| `known-failure` | P1.8b 已发现问题样本 | 失败不阻断，但错误类型变化要提示 |

P1.9 的具体分桶和统计口径见 `docs/p1-bench-compile-spec.md`。

## 结论

P1 结束后，项目的主要不确定性已经从“编译器是否存在”切换到“着色器前端是否可控”。

对后续最关键的判断是：

- P4 的核心不是再证明一次 Path A 可用
- P4 的核心是把 `MetalShaderCompiler + CommandMapper + 回退逻辑 + 缓存` 设计成一个能消化真实失败模式的系统

如果这一步做对，P5 会是在真实问题上逐步扩面；如果这一步做错，P5/P6 会不断被同一批编译失败和日志噪音拖住。
